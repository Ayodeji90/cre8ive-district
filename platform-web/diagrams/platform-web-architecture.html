Platform architecture · current implementation

One platform, independent AI services

The platform API owns customers, businesses, payments, jobs, persistence and review. The Website Agent's brand input comes directly from Branding Agent output; the API remains the platform control plane, not the source or relay for that brand package. Website generation is still a scaffold.

Integrated AI service Platform or external dependency Intended service data flow, not yet integrated

How a brand job moves through the system

01 · REQUEST

Product apps → Platform API

The API handles the user-facing workflow and platform rules. When brand generation is needed, it records/queues work rather than running a long AI task in the request.

02 · GENERATE

Queue → worker → Branding Agent

The worker calls the Branding Agent for strategy, logo, palette, fonts, copy and validation. The Branding Agent's output is the Website Agent's input; the intended data transfer is direct service-to-service, not through the platform API.

03 · REVIEW & DELIVER

Platform persists and completes

The API still owns users, business records, payments, job status and human review. It can coordinate jobs and permissions without becoming the source or relay of the brand data consumed by the Website Agent.

Which component owns what?

Frontend · apps/

Next.js marketing, customer platform and admin interfaces. These are clients; they do not own brand-generation workflows or persistence.

Platform API · api/

FastAPI endpoints, authentication, businesses, orders/payments, jobs, review, persistence, delivery and the adapter to AI services.

Branding Agent · services/branding-agent/

Independent HTTP service for brand AI operations and asset rendering. Its generated brand package is the input source for the Website Agent; provider credentials belong here.

Shared types · contracts/ and packages/

Intended place for cross-service request/result/event definitions and frontend API clients. A canonical, versioned schema package is still a follow-up.

Website Agent · services/website-agent/

Independent service boundary exists, but it currently exposes health and holds a relocated prompt only. The intended direct Branding Agent → Website Agent brand-package flow and website generation are not implemented yet.

Local runtime · docker-compose.yml

Runs PostgreSQL, Redis, API, worker, Branding Agent and Website Agent. Service separation is in place; not every service is product-connected yet.

Current limitation: structured or conversational brand intake clarification is not yet a complete end-to-end flow into the generation fields. Treat the Website Agent and canonical shared contracts as architecture foundations, not finished product features.
